# lark-a2a-hub 功能评审

评审日期：2026-11-05。范围：`/Users/jarod/Document/agent-node-adapter` 当前工作树（含已有未提交变更）；下列路径相对此根目录，行号按读取时源码。只读仓库，仅写本报告。
结论：正常路径的薄执行壳已具备，但审批、重复执行、终态保护与呈递存在实质缺陷，不宜把当前实现视为具备强制安全边界的无人值守中台。共 **30 项：阻塞 0、高 17、中 12、低 1**。

## 高严重度

### 01 [高] 文本关键字能覆盖结构化驳回
- 位置/证据：`src/kernel.mjs:379-384`：`decision === "approve"` 之外还接受 `msgText(m).includes("approved")`。
- 影响：`{"decision":"reject"}` 配合文本 `not approved` 仍返回 true；内存模拟已复现，违背标准 §8.3 的 DataPart 唯一判据。
- 最小修复：删除文本兜底，只接受可信枢纽针对当前 auth_request 的结构化决定；关联请求并以有效最新决定为准。

### 02 [高] 审批回调没有核验点击者是机主
- 位置/证据：`hub/event_receiver.py:135-145,168-175` 只读取 `action.value`、任务状态和 decision，没有读取 operator，也未核对 `HUB_OWNER_OPEN_ID`。
- 影响：非机主的有效卡片点击一旦到达处理器，也会批准/驳回任务；模拟非机主 operator 时写出三条记录并置 submitted。
- 最小修复：在任何写入前比较回调操作者身份与配置的机主身份，不匹配直接拒绝；同时绑定卡片与当前待批请求。

### 03 [高] 节点没有自己的副作用审批下限
- 位置/证据：`src/kernel.mjs:315,475-493` 仅把 `entry.side_effect` 写名片，是否审批完全取决于任务行 `Approval_Class === "approve"`。
- 影响：同一个 `side_effect:"write"` 命令收到漏标/伪标成非 approve 的任务就直接执行；外部建单者可绕过标准 §0 的机主审批红线。
- 最小修复：从本地可信命令配置导出最低审批要求，与任务标记取更严格者；写入、发送、支付等能力不得由任务行降低门槛。

### 04 [高] 未落实承诺的指令与数据隔离
- 位置/证据：`src/kernel.mjs:190-208` 直接拼接 Title、instruction、参数 JSON、answer 到 prompt；示例 `config/commands.example.json:17` 使用 `--dangerously-skip-permissions`。
- 影响：不可信参数/答复与控制提示同级进入有工具权限的 Agent，具备提示注入路径；这正是 `DESIGN.md:73` 要禁止、AGENTS 已承认尚未实现的边界。
- 最小修复：受信提示只引用独立的数据资源，不内联外部正文；明确数据来源并限制执行器工具权限，拒绝外部执行控制字段，不将“分文件”当成完整沙箱。

### 05 [高] 同节点双守护可以同时认领并执行同一任务
- 位置/证据：`src/kernel.mjs:401-407` 认领与回读只比较固定 `Claimed_By=this.cfg.node`；`bin/hub-node.mjs:36-38` 没有实例锁。
- 影响：自启守护与手工 daemon 并存时，两者读取同一 submitted 快照，都能通过校验；模拟实际得到两次执行。
- 最小修复：配置目录加单实例锁，并引入执行实例唯一租约/代次及回写 fencing；固定节点名不能用作执行所有权凭证。

### 06 [高] 陈旧快照和执行收尾可覆盖 canceled 等终态
- 位置/证据：`src/kernel.mjs:401-403,418-447,580-588` 使用扫表快照盲写 working/completed/submitted，执行期间不复查终态或所有权。
- 影响：枢纽在执行期间取消，节点仍继续操作并最终改为 completed；模拟已复现。队列中较后任务也可能在等待期间取消后被旧快照重启。
- 最小修复：认领前重新验证当前非终态，执行时监听取消/租约变化，停止子进程；每次状态提交须验证当前状态和本次租约，不能覆盖终态。

### 07 [高] 实际没有任务级幂等键查重
- 位置/证据：`src/kernel.mjs:468-473` 唯一“幂等对账”是按本 Task_ID 找 result；src/、hub/ 全文无 `Idempotency_Key` 读取。
- 影响：不同 Task_ID、相同业务幂等键的两行会各执行一次，模拟已复现；与 `DESIGN.md:36`、`docs/hub-integration.md:50-51` 明确承诺冲突。
- 最小修复：建单与派发均查重并持久化业务键执行记录；碰到在途/已交付键时复用对应工作，不再次执行。

### 08 [高] 心跳回收只在启动跑一次，运行中卡住永不恢复
- 位置/证据：`src/kernel.mjs:564-565` 是 `reclaimStale()` 唯一调用；`:410` 在心跳计时器和 try 之前读取参数。
- 影响：认领后读取消息失败会留下 working、无心跳、无 Run，主循环以后跳过它；模拟已复现。启动时回收请求失败也不会再补做。
- 最小修复：将回收加入周期对账，并让认领后的参数读取、心跳与所有异常处理都处于可清理的执行生命周期内。

### 09 [高] input-required 续跑绕过所有派发校验
- 位置/证据：`src/kernel.mjs:497-509` 仅检查 Claimed_By，随后直接 `execute(task, answers)`，不经过 `handleTask` 的审批/熔断/能力/carrier 检查。
- 影响：暂停期间撤销 Dispatchable、移除能力、改变审批要求或 carrier 离线都不阻止续跑；模拟未批准且 Hop=9 的待输入任务仍完成。
- 最小修复：把完整的本地策略与执行条件校验抽成共用入口，首次派发及每次续跑都执行，续跑仍保留原 Task_ID。

### 10 [高] 不带占位符的 agent carrier 命令静默直跑
- 位置/证据：`src/kernel.mjs:283-288`：有 `{prompt}` 才 `execFor`，否则调用 `this.runShell(command, prompt, ...)`。
- 影响：合法的 stdin 型 agent 模板即使声明 `context:"carrier"`、carrier 也在线，仍在守护语境执行；分支模拟已复现，违反“不静默降级”。
- 最小修复：stdin 分支也统一调用 `execFor(entry, command, prompt, timeout, cwd)`。

### 11 [高] 半写入消息被误当成交付，审批半写入也无法自愈
- 位置/证据：`src/kernel.mjs:138-145` 先写消息再写 Parts；`:469-471` 看到任意 result 即 completed；`:391` 看到 auth_request 就直接 return。
- 影响：result 行成功、正文写失败后，任务重入队会被关为 completed，但永久没有结果正文（模拟已复现）；auth_request 成功而状态更新失败则一直卡在 submitted。
- 最小修复：本地 outbox 保存待提交结果，以稳定 ID 幂等补齐缺失 Parts，再确认完成；对账验证内容完整性；已有待批消息仍应修复任务状态。

### 12 [高] 回执解析失败会重做已完成的业务操作
- 位置/证据：`src/kernel.mjs:271-277,418,435-441` 将进程成功后的 JSON 解析错误当作可重试业务失败。
- 影响：脚本已经发送消息/改数据，却因尾行损坏而重跑，最多造成三次副作用；`stdout="null"` 会在 need_input 取值处抛错，模拟已确认。
- 最小修复：区分“执行失败”和“执行成功但回执无效”，保留原输出、校验回执 schema；仅修复/重取回执或转人工，不自动重做成功操作。

### 13 [高] 问题呈递后不会再呈递最终结果
- 位置/证据：`hub/present_results.py:60-65,88-89` 标记并跳过 `Presented=Yes`；`src/kernel.mjs:430-447,509` 续跑及新状态不清此标记。
- 影响：input-required 呈递后正常 --mark，再收到答复并完成，扫描仍跳过该任务；第二轮问题也丢失。模拟 completed+Yes 输出零条。
- 最小修复：按状态消息/呈递版本去重，而非任务永久布尔值；至少在每个需重新呈递的状态迁移时清标记。

### 14 [高] 呈递扫描四张表都截断为 200 行
- 位置/证据：`hub/present_results.py:39-50,68-71` 固定 `--limit 200`，没有分页/继续读取。
- 影响：任一表超过 200 行就可能漏任务、消息、正文或 Run，且以后扫描仍只看这批记录；has_more 的模拟输入只调用一次并只返回 200 行。
- 最小修复：分页读全或按明确未呈递条件与关联 ID 查询，不能拿截断全表结果做完整对账。

### 15 [高] 超时只终止 shell，不终止整棵执行进程树
- 位置/证据：`src/kernel.mjs:228-236`、`src/carrier.mjs:91-99` 都用 `spawn(...,{shell:true,timeout:...})`，没有进程组终止。
- 影响：复合命令的子进程可在超时后继续副作用并持有管道；实测 30ms 杀掉 shell 后子进程仍在约 879ms 输出，Promise 才 close。
- 最小修复：统一管理独立进程组，超时/取消/退出先 TERM 后限时 KILL 整组，收敛 stdin/stdout 与 carrier 请求生命周期。

### 16 [高] stdin 的 EPIPE 能击穿守护异常处理
- 位置/证据：`src/kernel.mjs:235-238`、`src/carrier.mjs:98-101` 只监听 ChildProcess.error，没有监听 `p.stdin.error`。
- 影响：执行器提前退出而仍有信封写入时，Socket 发出未处理 error，Node 直接退出；本地大信封→`true` 复现退出码 1、Unhandled error/EPIPE。
- 最小修复：监听 stdin 错误并归入执行 Promise 的统一失败/清理路径，写入时处理背压，不能依赖 unhandledRejection 捕获 EventEmitter.error。

### 17 [高] README 的新装→setup 路径保留了不可用的旧示例能力
- 位置/证据：`install.sh:39-46` 先种 node/commands；`src/setup.mjs:248-263` 只在 commands 不存在时写绝对路径 echo。旧示例含 `node ../src/executors/echo.mjs` 和 lan-exec（`config/commands.example.json:10,24-31`）。
- 影响：安装目录为 `~/.hub-node/app`、cwd 为 `~/.hub-node`，该 echo 路径指错；旧 lan-exec 还触发 `doctor:100-101` 的 carrier 离线，使 setup 在注册自启前失败，而不是宣称的 echo-only 入列。
- 最小修复：安装阶段不抢先种可执行示例，或让 setup 明确认领未配置模板并生成正确的 echo-only 配置；不要覆盖用户真实能力配置。

## 中严重度

### 18 [中] 心跳回收不受重试上限约束
- 位置/证据：`src/kernel.mjs:368-372` 对所有陈旧 working 无条件 submitted、Retry_Count+1；`:456-493` 派发前也不检查超限。
- 影响：不断崩溃/丢心跳的任务能在重启回收后无限重跑；模拟 Retry_Count=2 仍回 submitted 并变成 3。
- 最小修复：明确并实施租约超时的重试预算，超限写 failed Run 与 notice 后终止，而不是无限回收。

### 19 [中] 配置热加载不会登记新增能力
- 位置/证据：`src/kernel.mjs:573-579` ensureCapabilities 只在 `_capsReady=false` 调用一次，随后只 loadCommands；`:479` 又要求技能同时在 cards 中。
- 影响：按 `README.md:71` 修改 commands 加能力后仍被 rejected，必须重启；已有名片的描述、副作用等变更也不会同步。
- 最小修复：检测配置版本变化并串行重新对账名片，登记成功后再启用该版本能力。

### 20 [中] 一次配置编辑错误会永久拒收队列任务
- 位置/证据：`src/kernel.mjs:83-89` 解析失败把 `this.commands={}`；`:578,479-483` 紧接着按无能力拒收到终态。
- 影响：用户编辑/非原子写入 commands 的短暂坏 JSON，被放大为真实任务永久 rejected，而非暂缓接单。
- 最小修复：保留最后一次校验成功的配置；新版本失败时告警并暂停新增派发，不把配置故障解释为业务能力不存在。

### 21 [中] carrier 可用性缓存可永久与表状态不一致
- 位置/证据：`src/kernel.mjs:307-311` 启动时设 `_carrierUp` 却跳过已有卡片；`:332-334` 状态相同就 return，且写表前先改缓存。
- 影响：守护重启时 carrier 已离线、卡片还 online，会永远不修正（模拟 online、零次更新）；同步写失败同样失去重试。
- 最小修复：首次启动强制校准已有卡片；只在全部写成功后提交缓存，失败保留待同步状态。

### 22 [中] 多轮续跑丢失问题、先前答复与执行上下文
- 位置/证据：`src/kernel.mjs:190-208,500-509` 只取最后一个 question 之后的 answer；`:267-270` 信封无历史、会话句柄或检查点。
- 影响：第二次续跑只收到第二次答复，连本次问题文本也没有；模拟 FIRST-ANSWER 与问题均不在新 prompt 中。任务号相同不等于执行上下文续接。
- 最小修复：按消息顺序与 In_Reply_To 提供完整相关对话，或通过执行器会话/检查点恢复；同时避免重复做已完成步骤。

### 23 [中] 消息 FilePart 在执行输入中被丢弃
- 位置/证据：`src/kernel.mjs:103-115,179-187,267-270` 只读取 text/data，JSON 信封只带参数与文字 instruction。
- 影响：标准 Parts 可表达的附件链接/文件名不会送给脚本或 Agent；带 FilePart 的模拟任务信封中完全没有该 URI。
- 最小修复：将按 Seq 排序的规范化 Parts/资源指针交给执行器，并遵守数据隔离；不可支持的输入模式应明确拒收而非无声忽略。

### 24 [中] 审批卡只显示上下文编号，不展示实际待执行内容
- 位置/证据：`hub/approval_watcher.py:29-44`：`payload=f1(task,"Context_ID")`，卡片只有 Title、节点、技能和这个编号，不读 instruction/参数/auth_request。
- 影响：不同危险操作可以拥有同样的标题与技能，机主无法从卡片判断自己批准了什么；编号不是操作说明。
- 最小修复：展示当前 auth_request、必要且脱敏的操作参数及影响范围，并把审批绑定到这些内容的版本。

### 25 [中] Runs 不是标准承诺的执行起止台账
- 位置/证据：`src/kernel.mjs:165-173` 创建时同时写 Started_At/Finished_At；`:418-436` 都在执行结束后才 writeRun，和 `docs/standard.md:146` 的“认领后 Runs 开行”不符。
- 影响：执行中或进程崩溃时没有该次 Run，Latest_Run 仍可能指向旧段，无法靠总线区分“尚未启动”和“执行中断”。
- 最小修复：认领成功时建立本次 Run 并写 Latest_Run，结束时只关闭此行；Run 不属于 Messages/Parts 的只追加禁改范围。

### 26 [中] doctor 把 socket 在线当成局域网能力可用
- 位置/证据：`src/doctor.mjs:95-100` 仅 pingCarrier 就输出“能力…可用”；`DESIGN.md:88` 承诺探测实际执行者的局域网可达性，`:87` 又记录终端 carrier 仍不可达的实测反例。
- 影响：自检通过不能验证该能力能干活；`README.md:78-88` 也没有传达 DESIGN 的环境限定，容易按错误保证部署。
- 最小修复：将 socket 存活与资源可达性分开报告，提供用户指定目标的只读执行探针；未探测明确标“未验证”，README 补充限定。

### 27 [中] 枢纽 20 分钟补呈安全网没有部署入口
- 位置/证据：`hub/event_receiver.py:103-120` 只在新事件到达时调扫描；`hub/agent-hub-receiver.service:9-12` 只启动接收器；`hub/README.md:31-35` 只安排审批 watcher。对比 `docs/hub-integration.md:71-72` 的周期补呈承诺。
- 影响：按速记部署、漏掉最后一次事件后，未呈递任务可无限等待，而非 20 分钟补回；审批 watcher 不扫描终态结果。
- 最小修复：提供或明确要求安装周期呈递扫描 timer/cron，复用同一队列去重入口，不以新事件作为补呈前提。

### 28 [中] 自愈脚本失败仍报告成功
- 位置/证据：`hub/ensure_receiver.sh:8-12` 不检查 cp/start 就打印 REPAIRED、exit 0；`:19-22` 即使打印 BROKEN 也 exit 0。
- 影响：缺少权限、源 unit 不存在或启动失败时，上层巡检收到成功状态，无法触发故障处理。
- 最小修复：逐步检查安装/启动结果并确认 is-active；修复失败返回非零，只有健康或确已修复才返回零。

### 29 [中] 手工 Secret 输入没有隐藏回显
- 位置/证据：`src/setup.mjs:119-125,166-168` 用普通 `readline.question` 收集 App Secret，却声称不会显示在任何日志里。
